# 每日增量排名预聚合验证

日期：2026-10-13。Node.js 22.16.0、pnpm 10.28.2，本地合成 SQLite；未使用生产数据、凭据或真实 Provider。

## 对比边界

基线为 `0efac8d4e93fa8feeac4782aa8df8a15acf3e3e9` 的 `AttributionStore`，修改前冻结为独立模块。两版读取同一数据库，按完整 `rankingsPage` 返回对象比较，包括数组顺序、分页总数、NULL、零值、估算配置及最新展示信息，不忽略字段。

经用户确认，管理 API 的时间筛选改为请求时区的自然日：`from` 向日初取整，非日界线的 `to` 向下一日取整，已对齐的 `to` 仍为排他上界。响应返回实际范围。差分验证使用相同的实际时间范围；此项明确的时间粒度调整不伪装为精确时间筛选等价。

## 实现及 SQL 验证

- 按时区、namespace、Agent、Session、自然日登记分区，输入计数、coverage、最新元数据和对话内容分别持久化。汇总表按分区和能力／分类聚簇，查询直接读取所需列。
- 来源写入在原事务中标记受影响分区。后台只读 Worker 每次聚合一个分区，写入端检查修订号后原子替换全部汇总表；旧结果不能覆盖新计数。
- 历史发现每批最多读取 500 条上下文及 500 条内容元数据。未完成发现的时区使用原查询；已发现范围合并已完成分区与脏分区的实时聚合。调用去重和精确 P50/P95 保留原算法。
- 排序只读取该排序需要的调用字段和输入指标；非内容排序仅读取内容分类身份。估算配置、字节详情和展示元数据在分页后只查询选中的能力。
- 日期连接分离 NULL 时间分支，使用现有 `agent_usage_contexts_subject` 的日期范围；完整聚合详情命中 `PRIMARY KEY(partition_id, capability_key, ordinal)`。
- 专项测试用 SQL 函数捕获不必要读取：完整日查询不读取源输入 token 行，分页不读取页外字节详情、展示元数据或内容估算配置。执行计划断言确认能力主键和日期范围访问路径。
- 显式 Session 删除在同一事务立即清除分区和汇总行；回填期间发生删除、修订或提交失败均有回归测试。分区状态不参与原始事件清理资格判断。

## 审核修复验证

此次审核发现的三个问题已修复，新增六项回归用例在修复前全部失败，修复后全部通过：

- 重复午夜：`Asia/Amman` 的 2021-10-29 必须从 `2021-10-28T21:00:00Z` 开始，不能选择第二次午夜。验证第一段午夜的上下文和内容计数不会在预聚合后消失，第二段午夜的迟到数据在脏分区和重建后也与明细路径一致；已有 23／25 小时、午夜跳过及整日跳过测试继续通过。
- 页外 coverage：在去重和聚合前下推当前页能力集合。有日期和无时间戳分区均用 SQL 读取探针验证页外 coverage 为零次读取；执行计划命中输入索引的 `(context_id, capability_key)` 和汇总表的 `(partition_id, capability_key)`。
- 单侧内容排序：参数／结果 token 的读取条件直接放在源查询和每日 UNION 各分支内。仅在外层加 CASE 仍会提前读取无关 token，因此同时测试原始回退、已完成汇总和脏分区。排序保留全部类别身份及总数，当页详情仍返回完整指标。

下列差分结果和性能数据均在这些修复完成后重新取得。SQL 读取探针证明逻辑读取范围，不等同于物理磁盘 I/O 测量。

## 一致性

`scripts/verify-usage-ranking-versions.ts` 比较 18 种筛选 × 4 种维度 × 12 种排序 × 3 种分页 × 5 个状态，共 **12,960 组**，全部相等。

五个状态为：原紧凑输入、完整每日聚合、强制明细回退、迟到／修订／删除后的脏分区、重新聚合后。筛选包含 namespace、Agent、Session、Runtime、上下界、空范围、缺失时间及多时区；数据包含未知和已知零值、多估算配置、四类 coverage、首次／重复／未知首次、跨日期 context-only 调用、执行失败与精确百分位数。单独回归覆盖夏令时的 23／25 小时自然日、非整小时时区、历史发现重启、原子提交失败和真实只读 Worker。

## 维护成本

同一基准同时登记 UTC 和 Asia/Singapore，首次构建 **560 个分区耗时 8,802 ms**，数据库页增长 **12,238,848 字节（约 11.7 MiB）**。脚本连续执行，不包含实际后台每轮主动休息及 Worker 启动时间。

修改一个上下文的 coverage 后，只重建两个时区对应的 **2 / 560 个分区，耗时 35 ms**，不是全范围重算。

对 500 个上下文及 500 条内容记录做更新，在回滚的合成事务内交替测量五轮。关闭每日失效触发器时中位数 **2.55 ms**，启用两个时区失效维护时 **20.24 ms**，增加约 **17.69 ms / 1,000 次更新**。这只测事务体，不包含提交／fsync；每增加一个使用过的时区都会增加汇总空间及维护开销。

## 复现

在仓库根目录冻结旧查询模块，依赖解析到当前源树：

```sh
rtk proxy python3 - <<'PY'
from pathlib import Path
import subprocess
import tempfile
root = Path.cwd()
source = subprocess.check_output([
    'rtk', 'proxy', 'git', 'show',
    '0efac8d4e93fa8feeac4782aa8df8a15acf3e3e9:src/agent-usage/storage/attribution-store.ts'
], text=True)
source = source.replace('from "../', 'from "' + str(root / 'src/agent-usage') + '/')
source = source.replace('from "./', 'from "' + str(root / 'src/agent-usage/storage') + '/')
path = Path(tempfile.mkdtemp(prefix='usage-ranking-baseline-')) / 'attribution-store.ts'
path.write_text(source)
print(path)
PY
```

使用 Node.js 22，把输出路径传给验证脚本：

```sh
rtk proxy corepack pnpm exec tsx scripts/verify-usage-ranking-versions.ts <baseline-module>
rtk proxy corepack pnpm exec tsx scripts/benchmark-usage-ranking-versions.ts <baseline-module> 4000
```

基准默认 1,000 个上下文，可指定 1–5,000 个。性能脚本直接构造紧凑输入，公开写入和失效路径由差分及回归测试验证；所有合成数据库在 `finally` 中清除。性能测量应独立运行。
